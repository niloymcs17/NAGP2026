# Inter-Service Communication Writeup

This document describes how the microservices in the **Employee Leave Management Portal** communicate, exchange data, and handles events, along with architectural assumptions.

---

## 1. Communication Patterns

The architecture uses a hybrid communication model:
1. **Synchronous Request-Response (via Gateway)**: Client requests (such as logging in, checking balances, submitting leave requests, and approving requests) are routed synchronously via HTTP REST calls through the API Gateway downstream to individual services.
2. **Asynchronous Event-Driven Messaging (via RabbitMQ)**: When side-effects occur (like employee profile creation or leave requests changing status), the services publish events to the RabbitMQ broker. Downstream listener services consume these events asynchronously. This decouples the services, guarantees eventual consistency, and improves fault tolerance.

---

## 2. RabbitMQ Messaging Exchange Schema

RabbitMQ is used for handling event streams. We use **Topic Exchanges** to enable flexible routing pattern matching.

```
                  [ Employee Service ]
                           │
                           ▼ (Publish)
                  ┌─────────────────┐
                  │ employee.exch   │ (Exchange)
                  └────────┬────────┘
                           │ routingKey: "employee.created"
                           ▼
                  ┌─────────────────┐
                  │ employee.queue  │ (Queue)
                  └────────┬────────┘
                           │
                           ▼ (Consume)
             [ Leave Management Service ]
                           │
                           ▼ (Publish)
                  ┌─────────────────┐
                  │   leave.exch    │ (Exchange)
                  └────────┬────────┘
                           │ routingKey: "leave.notification"
                           ▼
                  ┌─────────────────┐
                  │   leave.queue   │ (Queue)
                  └────────┬────────┘
                           │
                           ▼ (Consume)
               [ Notification Service ]
                           │
                           ▼
                  [ Write System Logs ]
```

### Event 1: Employee Created
* **Publisher**: `employee-service` (when a new employee is created)
* **Exchange**: `employee.exchange` (Type: `topic`)
* **Routing Key**: `employee.created`
* **Queue**: `employee.created.queue`
* **Consumer**: `leave-management-service`
* **Action taken**: The consumer automatically initializes default leave balances for the new employee (12 Casual, 10 Sick, 15 Privilege).

### Event 2: Leave Notification
* **Publisher**: `leave-management-service` (when leaves are applied, approved, rejected, or cancelled)
* **Exchange**: `leave.exchange` (Type: `topic`)
* **Routing Key**: `leave.notification`
* **Queue**: `leave.notification.queue`
* **Consumer**: `notification-service`
* **Action taken**: The consumer formats the event payload and logs it to the console log stream as a simulated notification.

## 4. Key Architectural Assumptions

To deliver a reliable Minimum Viable Product (MVP), we made the following assumptions:

1. **User Identity Consistency**: The user's ID generated by the `authentication-service` (primary key in the `users` table) is identical to the `id` of their profile record in the `employee-service` and their `employeeId` in the `leave-management-service`. When a new employee is created via `POST /employees`, the manager provides the ID corresponding to the authenticated user account.
2. **Eventual Consistency**: When an employee is created in the `employee-service`, the creation HTTP request returns successfully to the client immediately after persisting the user. The leave balances are initialized asynchronously. If RabbitMQ is busy or temporarily down, the event is queued and processed when the message broker recovers.
3. **No Real Email/SMS Integration**: To simplify deployment, notifications are logged to the standard console output stream. The `notification-service` acts as the simulated notification broker, consuming `leave.notification` events and logging them in a structured console box.
4. **H2 In-Memory Storage**: Data persists in-memory for the duration of the container lifetimes. Each service runs its own isolated H2 database instance (e.g. `authdb` for Auth, `employeedb` for Employee, `leavedb` for Leave) to maintain microservice data isolation. Re-spinning the containers resets the databases to their pre-seeded initial states.
5. **Centralized Authentication**: Services assume that any request reaching them has already had its JWT Bearer token validated by the API Gateway's `JwtAuthenticationFilter`. The microservices extract the user's role and ID from the headers injected by the Gateway (`X-User-Id`, `X-User-Role`, `X-User-Username`) to perform localized business rule authorization checks.
